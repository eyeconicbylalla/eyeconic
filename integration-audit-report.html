Eyeconic Integration Audit

Pre-implementation audit of the Eyeconic Mentorship App (C:\Projects\eyeconic-app) and the Eyeconic Website (C:\Projects\eyeconic-main), covering architecture, data ownership, identity, and the safest integration approach. Nothing was modified.

Mentorship App · Expo + Express + Mongo Website · Vite React + Express + Mongo Two separate Atlas clusters (verified) Audit only — no changes made

Verdict at a glance

Recommended architecture — Option B: the Website's server calls a new, minimal set of read-only, service-authenticated endpoints on the Mentorship App API (/api/integration/*). The Website keeps its own database for everything it owns (blogs, CRM, predictor reference data); the App remains the single source of truth for students, questions, tests, attempts and analytics. The browser never talks to the App API directly, so no CORS changes are needed.

Top blockers before implementation: ① no exam rank/branch/cutoff dataset exists anywhere — the Rank & Branch and Desired Branch predictors have no data foundation yet; ② two independent identity stores with no shared key except email (mutable in the App); ③ hardcoded admin credentials shipped in the Website client bundle must be fixed before the Website server can be trusted with integration credentials; ④ the eight listed website features exist as a requirements list only — no written spec was found in either repo.

Authentication & Identity

App identity

  • Canonical ID: users._id (ObjectId)
  • Login: email + password; email unique, trimmed, lowercased (models/User.js)
  • JWT 7d, {userId, role}; guest JWTs scoped kind:'guest'
  • Phone: optional, not unique, not verified
  • No human-readable student ID (imports are email,name CSV)

Website identity

  • Own users collection on a different cluster — IDs are unrelated ObjectIds
  • JWT 7d, {user:{id}}, different secret; student signup open (no OTP on the wire — the OTP endpoints exist but SignupModal never calls them)
  • Admin: hardcoded credentials in client bundle + query strings

Cross-system recognition

  • Only practical shared key today: email. It is unique + normalized in the App; the Website model marks it unique but normalization on write was not verified (flagged below).
  • Email is mutable in the App — PUT /api/users/:id/email (admin) can change it, so email is a bootstrap key, not a permanent join key.
  • Security concerns with email as identifier: (1) enumerable/joinable across the two systems; (2) a person can create a Website account with an email already belonging to an App student (or vice versa) — no verification bridges them, so lookups could return another person's data if trust is naive; (3) App guest leads share emails across records by design; (4) family/shared inboxes. Conclusion: email may bootstrap a link, but the link itself should be an explicit mapping (App user._id ↔ Website account) established at login through the App's authority, not free-text lookup.
  • Recommended shape (not implemented): Website authenticates the student through the App (App issues the identity), or the Website server verifies a user-supplied App token by calling an App endpoint — either way the App remains the identity authority.

Data Ownership Model

App Mentorship App owns

  • Student/mentor/admin identities & credentials (users)
  • Subjects, chapters/topics (legacy), Question Bank
  • Quizzes/tests (incl. Grand Tests) & assignments
  • All attempts & scores (quizattempts, guestattempts)
  • Analytics computation (percentile, rank, breakdowns)
  • Guest leads & OTP, proctoring data, app settings

Website Website owns

  • Blog CMS (blogs, categories, tags, media assets)
  • Marketing CRM fields on its own users (calledStatus, buyStatus, batchInterest, adminNotes)
  • New reference datasets: marks→rank mapping, branch/college cutoffs, platform comparison content
  • Predictor inputs/outputs & snapshots it computes for visitors
  • Daily-PYQ rotation schedule, CCT delivery config (presentation concerns)
  • Its own sessions/UI state

Shared Shared / read-only

  • Student profile, attempts, performance, question metadata → flow App → Website, read-only
  • Identity link (App user ↔ Website account) — established once via App-verified login; owned by the Website DB, keyed by App user._id
  • Nothing in the Website writes to App collections through integration

Final Recommendation

10.1 Architecture

Option B — API-based, server-to-server, read-only. The Website's Express server is the only component that talks to the App API, using a scoped service credential; the App exposes a small versioned read-only surface (/api/integration/v1/*); each product keeps its own database. No schema changes, no shared credentials, no browser-visible CORS surface.

10.3 Required integration components

  • App: integration router (read-only endpoints, §7) + service-auth middleware + rate limiting; explicitly enabled in featureAvailability.js as its own feature flag.
  • Website server: integration client module (timeout, retry, cache), config for the service credential, response shaping, graceful degradation when the App API is cold.
  • Website DB: identity-link storage (App user._id ↔ Website account) + new reference collections (rank/cutoff/platform datasets) — Website-owned.
  • Pre-req hardening: replace the Website's hardcoded admin auth; add rate limiting; move OTP to persistent storage.

10.4 What must NOT change

  • The App's schemas, grading logic (utils/grading.js), analytics (utils/analytics.js), and section-locking/duration enforcement.
  • The App's auth model (JWT shape, OTP flows, guest scoping) and the feature-freeze mechanism.
  • Direct write access from the Website to the App's cluster (never granted).
